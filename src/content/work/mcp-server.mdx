## 1. Context

Answering questions is the easy half of AI. The harder half is letting an assistant act on real business tools, safely. This server was built to do that for two workflows: trading analysis and sales outreach.

<Placeholder>Owner to supply: which AI clients the server is used with, and whether trading and sales serve one business or two.</Placeholder>

## 2. Problem

Useful work on trading scripts and sales outreach involved many small, repetitive steps across tools. An assistant that could only talk about those steps saved nothing. One that could take them without a check was not acceptable.

## 3. Decisions

- **Expose tools, not a chat.** The server describes typed tools the assistant can call: locate a script, start a backtest, research a prospect, prepare outreach.
- **Confirmation on every action that changes state.** The assistant proposes; a person approves; then it runs.
- **The same pattern generalises.** Any team can point an assistant at its own CRM, ERP or internal systems the same way.

<Placeholder>Owner to supply: options rejected and any limits placed on what tools may do.</Placeholder>

## 4. Architecture

An AI assistant connects to the MCP server. The server exposes tools for trading (locate scripts, start backtests, identify candidate entry and exit points, support trade entry and exit) and for sales (research prospects, prepare personalised outreach, automate outreach steps). Each state-changing action waits for a person to confirm.

## 5. Where humans stay in the loop

<ReviewMark label="Person confirms each action" />

This project is the clearest case of the principle. Trade entry and exit, and every outreach send, are proposed by the assistant and confirmed by a person. The server makes the assistant capable; the confirmation keeps it accountable.
